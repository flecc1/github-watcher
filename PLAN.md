# GitHub Watcher --- план разработки

## 1. Цель проекта

Создать личного Telegram-бота на Go, который собирает статистику по
выбранным публичным GitHub-репозиториям, параллельно обрабатывает
запросы к GitHub API и сохраняет список репозиториев и историю
статистики в PostgreSQL.

**Главная учебная цель:** применить конкурентность Go на реальной
задаче: goroutines, channels, worker pool, `select`, `sync.WaitGroup`,
отмена работы, безопасная работа с общими данными и тестирование на data
races.

Проект делается для личного использования. Не строить полноценный SaaS и
не добавлять инфраструктуру без необходимости.

## 2. MVP: функциональные требования

### Telegram-команды

-   `/start` --- краткая справка и доступные команды.
-   `/add owner/repo` --- добавить публичный репозиторий.
-   `/list` --- показать отслеживаемые репозитории.
-   `/stats` --- параллельно собрать актуальную статистику по всем
    сохранённым репозиториям и прислать сводку.
-   `/remove owner/repo` --- удалить репозиторий из списка.

### Данные по каждому репозиторию

-   Полное имя `owner/repo` и ссылка.
-   Количество stars и forks.
-   Наличие README.
-   Количество открытых issues.
-   Количество открытых pull requests.
-   Дата последнего коммита.
-   Количество коммитов за последние 7 дней.
-   Время сбора статистики.

Часть данных можно получить разными запросами GitHub REST API. Нужно
учитывать пагинацию, ошибки API и ограничения частоты запросов. Для MVP
достаточно публичных репозиториев.

### Поведение при ошибках

-   Ошибка одного репозитория не должна отменять сбор статистики для
    остальных.
-   Результат каждой задачи должен содержать либо статистику, либо
    понятную ошибку.
-   Если GitHub API вернул ошибку или тайм-аут, включить это в итоговый
    отчёт.
-   Не записывать неудачный или неполный результат как полноценный
    успешный снимок статистики.
-   Не выводить Telegram-токен и другие секреты в логи.

## 3. Хранение в PostgreSQL

Минимальная модель данных:

### `repositories`

-   `id` --- первичный ключ.
-   `owner` --- владелец репозитория.
-   `name` --- имя репозитория.
-   `full_name` --- полное имя `owner/repo`, уникальное.
-   `added_at` --- дата добавления.

### `repository_snapshots`

-   `id` --- первичный ключ.
-   `repository_id` --- внешний ключ на `repositories`.
-   `stars` и `forks`.
-   `open_issues` и `open_pull_requests`.
-   `has_readme`.
-   `last_commit_at`.
-   `commits_last_7_days`.
-   `collected_at` --- время сбора статистики.

История снимков позволит позже сравнивать изменения. При первом MVP
достаточно сохранять снимок после успешного сбора статистики.

### Требования к БД

-   Использовать PostgreSQL и `database/sql` с подходящим драйвером.
-   Запросы должны использовать параметры, а не конкатенацию
    пользовательских строк.
-   Создать миграции схемы.
-   Не держать транзакцию открытой во время HTTP-запросов к GitHub.
-   Обрабатывать ошибки чтения и записи в БД.

## 4. Конкурентная архитектура

Предлагаемый поток для команды `/stats`:

1.  Получить список репозиториев из PostgreSQL.
2.  Создать ограниченное число workers, например 3.
3.  Передать задачи в канал очереди.
4.  Каждый worker собирает статистику для одного репозитория через
    GitHub API.
5.  Workers отправляют результаты в канал результатов. Результат
    включает идентификатор репозитория, статистику при успехе и ошибку
    при неудаче.
6.  Координатор получает все результаты и учитывает частичные ошибки.
7.  Сохранить успешные снимки в PostgreSQL.
8.  Сформировать и отправить итоговый Telegram-отчёт.

### Правила конкурентности

-   Использовать один переиспользуемый `http.Client` с тайм-аутом.
-   Ограничивать количество одновременно выполняющихся задач worker
    pool.
-   Заранее определить, кто закрывает канал задач и кто закрывает канал
    результатов.
-   Не закрывать канал результатов, пока workers ещё могут в него
    писать.
-   Обеспечить ожидание завершения workers через `sync.WaitGroup` или
    эквивалентную понятную схему.
-   Передавать ошибки вместе с результатами, чтобы ошибка одного worker
    не блокировала остальные.
-   Использовать `context` для отмены HTTP-запросов и завершения работы.
-   Не добавлять mutex без необходимости. Предпочитать передачу
    результатов через каналы и единственного владельца агрегируемого
    состояния.
-   Если появится общий изменяемый кэш или состояние, отдельно решить,
    нужен ли `sync.Mutex`/`sync.RWMutex`.

## 5. Предлагаемое разделение ответственности

Структуру пакетов выбрать после краткого проектирования; не дробить
проект на множество мелких пакетов без необходимости. Логически нужны
следующие части:

-   **Telegram bot** --- приём команд, проверка аргументов, отправка
    сообщений.
-   **GitHub client** --- HTTP-запросы к GitHub API и преобразование
    ответов в структуры проекта.
-   **Statistics service** --- конкурентная координация задач, worker
    pool, сбор частичных результатов.
-   **Repository storage** --- операции с PostgreSQL: добавление,
    список, удаление репозиториев и сохранение снимков.
-   **Configuration** --- чтение токенов, DSN и других настроек из
    переменных окружения.
-   **Report formatter** --- преобразование статистики и ошибок в
    понятный Telegram-текст.

Не нужно вводить интерфейсы для каждого типа автоматически. Добавлять
интерфейс там, где он помогает отделить зависимость или упростить
тестирование.

## 6. Этапы разработки

### Этап 1. Подготовка --- 30--60 минут

-   [ ] Создать или переименовать GitHub-репозиторий в `github-watcher`.
-   [ ] Инициализировать Go-модуль.
-   [ ] Создать Telegram-бота через BotFather и сохранить токен в
    переменной окружения.
-   [ ] Подготовить PostgreSQL и конфигурацию подключения.
-   [ ] Выбрать библиотеку Telegram Bot API и драйвер PostgreSQL.

**Результат:** приложение запускается с конфигурацией из окружения,
секреты не хранятся в Git.

### Этап 2. Telegram-команды --- 1--2 часа

-   [ ] Реализовать `/start`.
-   [ ] Разобрать формат `owner/repo`.
-   [ ] Добавить `/add`, `/list` и `/remove`.
-   [ ] Проверить некорректные аргументы и ответы пользователю.

На этом этапе команды могут использовать временное хранилище, если так
проще проверять Telegram-интеграцию; затем подключить PostgreSQL.

### Этап 3. PostgreSQL --- 1--2 часа

-   [ ] Создать миграции.
-   [ ] Реализовать добавление и получение репозиториев.
-   [ ] Реализовать удаление репозитория.
-   [ ] Добавить сохранение успешных снимков статистики.
-   [ ] Проверить повторное добавление одного и того же репозитория.

### Этап 4. GitHub API --- 2--3 часа

-   [ ] Реализовать получение основных метаданных репозитория.
-   [ ] Проверить наличие README.
-   [ ] Получать открытые pull requests.
-   [ ] Получать дату последнего коммита и число коммитов за последние 7
    дней.
-   [ ] Разделить ошибки HTTP, ошибки API и ошибки декодирования ответа.
-   [ ] Добавить тайм-ауты и учесть rate limits.

Сначала проверить GitHub-клиент на одном репозитории; затем подключать
его к конкурентному сбору.

### Этап 5. Worker pool и каналы --- 2--3 часа

-   [ ] Определить тип задачи и тип результата.
-   [ ] Создать канал задач и канал результатов.
-   [ ] Запустить фиксированное количество workers.
-   [ ] Передавать каждому worker задачу по одному репозиторию.
-   [ ] Обеспечить корректное закрытие каналов и ожидание workers.
-   [ ] Собирать успешные результаты и ошибки без потери результатов.
-   [ ] Сохранять успешные снимки и формировать единый отчёт.
-   [ ] Проверить поведение на нескольких репозиториях и при ошибке
    одного из них.

### Этап 6. Тесты и надёжность --- 2--3 часа

-   [ ] Протестировать разбор аргументов команд.
-   [ ] Протестировать форматирование отчёта.
-   [ ] Протестировать обработку успешных и ошибочных ответов GitHub
    API.
-   [ ] Проверить частичные ошибки конкурентного сбора.
-   [ ] Проверить, что все workers завершаются и ожидание не зависает.
-   [ ] Запустить тесты с race detector: `go test -race ./...`.
-   [ ] Проверить обработку отмены и тайм-аутов.
-   [ ] Убедиться, что секреты не попадают в репозиторий и логи.

### Этап 7. Документация --- 30--60 минут

-   [ ] Написать README с назначением проекта и командами бота.
-   [ ] Описать необходимые переменные окружения.
-   [ ] Добавить инструкцию создания БД и запуска миграций.
-   [ ] Описать устройство worker pool и каналов.
-   [ ] Указать ограничения MVP.

## 7. Оценка времени

Ориентир для самостоятельной работы:

  Работа                                        Время
  --------------------------------- -----------------
  Подготовка и конфигурация                0,5--1 час
  Telegram-команды                          1--2 часа
  PostgreSQL и миграции                     1--2 часа
  GitHub API                                2--3 часа
  Конкурентный сбор                         2--3 часа
  Тесты, проверка ошибок и README         2,5--4 часа
  **Итого**                           **9--15 часов**

Это оценка, а не дедлайн. Если одновременно разбираться с
Telegram-библиотекой, GitHub API и конкурентностью, реалистично выделить
2--4 вечера или выходные. Не нужно торопиться ради завершения за два
дня.

## 8. Что из глав 8--9 книги закрепляется

### Глава 8 --- Goroutines and Channels

-   Goroutines: независимый сбор статистики репозиториев.
-   Channels: передача задач и результатов.
-   Параллельная обработка коллекции репозиториев.
-   `select`: применить там, где действительно нужно одновременно
    ожидать результат или отмену.
-   Cancellation: отмена HTTP-запросов и завершение работы.
-   Координация завершения: workers должны закончить работу до закрытия
    канала результатов.

### Глава 9 --- Concurrency with Shared Variables

-   Race conditions: найти возможные гонки в общем изменяемом состоянии.
-   `sync.Mutex` и `sync.RWMutex`: изучить на конкретном примере, если в
    проекте появится состояние, которое действительно разделяют
    горутины.
-   Memory synchronization: понимать, как синхронизация и каналы влияют
    на видимость результатов.
-   `sync.Once`: не требуется для MVP; можно применить только при
    наличии подходящей однократной инициализации.
-   Race detector: запустить `go test -race ./...`.
-   Общие данные: по возможности организовать сбор так, чтобы один
    координатор владел агрегированием результатов.

**Важно:** не все темы главы 9 обязательно появятся естественным образом
в MVP. Не нужно добавлять mutex или `sync.Once` только ради отметки.
Лучше понимать, почему конкретный инструмент нужен или не нужен.

## 9. Идеи для будущих улучшений

Не включать в MVP; возвращаться к ним после работающей первой версии.

1.  Автоматический сбор статистики по расписанию.
2.  Уведомления о новых релизах и изменениях GitHub Actions.
3.  Сравнение снимков статистики за неделю или месяц.
4.  Конфигурируемое число workers и ограничения GitHub API.
5.  Повторные попытки с задержкой для временных ошибок.
6.  Поддержка нескольких Telegram-пользователей.
7.  Docker Compose для запуска приложения и PostgreSQL.
8.  Дополнительные метрики и бенчмарки для сравнения последовательного и
    конкурентного сбора.

## 10. Критерии готовности MVP

-   [ ] Бот запускается локально и получает Telegram-команды.
-   [ ] Можно добавлять, просматривать и удалять публичные репозитории.
-   [ ] `/stats` собирает статистику по всем добавленным репозиториям
    конкурентно.
-   [ ] Количество workers ограничено.
-   [ ] Результаты и история статистики сохраняются в PostgreSQL.
-   [ ] Ошибка одного репозитория не мешает обработке остальных.
-   [ ] Тайм-ауты и отмена не оставляют зависших workers.
-   [ ] Тесты проходят, а `go test -race ./...` не обнаруживает гонок в
    покрытых тестами сценариях.
-   [ ] README объясняет настройку и запуск проекта.

## Принцип работы

Сначала спроектировать поток задач и результатов, затем реализовывать по
этапам. Не писать весь проект одним большим блоком и не добавлять
технологии ради резюме. Главная цель --- самостоятельно разобраться в
конкурентной обработке и уметь объяснить каждое архитектурное решение.
